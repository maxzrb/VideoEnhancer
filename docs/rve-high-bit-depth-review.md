## 包内问题

### 1. [P1] 忽略带流标识的像素格式，覆盖当前默认 12bit 4:4:4 输出

位置：候选 `backend/src/utils/PixelFormat.py:31–44`；调用点 `backend/src/FFmpegBuffers.py:406`。

`high_depth_encoder_args` 只识别完全等于 `-pix_fmt` 的选项。当前仓库 `cli/VideoEncodingDefaults.cs:6` 默认使用 `-pix_fmt:v yuv444p12le`。将该配置交给新函数，实际返回：

```text
-c:v libsvtav1 -pix_fmt:v yuv444p12le -pix_fmt yuv420p10le
```

后追加的格式会覆盖用户原定格式。该缺陷会将更高精度的 12bit 4:4:4 请求改为 10bit 4:2:0，某些编码器/配置组合也可能因此报错。应统一识别 `-pix_fmt` 及匹配输出视频流的标识形式，按最后一个有效选项处理，保留用户已经指定的高位深格式。

证据：`encoder-default-probe.json`，使用包内原函数和本机真实 FFmpeg 编码器能力查询。

### 2. [P1] OpenCV 文件接口破坏 Windows 中文图片路径

位置：候选 `backend/rve-image-backend.py:240`、`:272`，时序图片提取还有 `:208`。

原先通过 Pillow 读取/保存文件，现在直接向 `cv2.imread` / `cv2.imwrite` 传 Unicode 路径。本机实际运行库中，同内容的 ASCII 路径 16bit PNG 可读，`中文图片.png` 则返回 `None`。写出 `out_中文图片.png` 时 `imwrite` 返回 `True`，但预期路径不存在，实际生成了乱码名称 `out_涓枃鍥剧墖.png`，可能使任务报告成功而用户找不到目标文件。

高位深与 Unicode 文件路径可同时保留：用 Python `Path.read_bytes` + `np.frombuffer` + `cv2.imdecode` 读入；用 `cv2.imencode` + `Path.write_bytes` 写出。应覆盖普通图片与时序图片中全部新增的 OpenCV 文件接口。

证据：`probe-results.json` 和项目证据目录中的实际图片文件。没有修改用户图片。

### 3. [P2] 均值类转场检测没有同步量纲

位置：候选 `backend/src/utils/Frame.py:73`、`:128`；消费者 `backend/src/utils/SceneDetect.py:28`、`:65`、`:113`。

主帧从 0–255 改为 0–65535，而 `mean`、`mean_diff`、`mean_segmented` 检测器仍比较 `threshold * 10`。敏感度 4 时，对两张仅由灰阶 100 变为 101 的均匀帧，三个检测器均返回转场；旧的 8bit 量纲下，变化 1 小于阈值 40，不应触发。误判会让补帧器走转场复制路径。

建议保持主帧高精度，只在检测器输入侧统一归一化量纲，或对阈值作相应缩放。本轮默认 `pyscenedetect` 对照返回 False，不把所有转场算法都判为损坏。

### 4. [P2] 数字输出流编码器被误判为未指定

位置：候选 `backend/src/utils/PixelFormat.py:45–49`。

函数没有识别项目已经修复并支持的 `-c:0` / `-codec:0`，以及其他合法视频流标识形式。例如 `-c:0 ffv1 -pix_fmt gbrp16le` 被当作默认 `libx264` 检查，直接抛出“不支持 gbrp16le”；使用 10bit 格式时，还可能追加 `-c:v libx264` 覆盖原编码器。`-c:v:0 ffv1` 对照可通过。应与 `VideoEncodingDefaults` 的输出流约定一致，而不是只匹配少数固定字符串。

### 5. [P2] 包内转换器回退了主线已有的 ONNX 中文路径修复

位置：候选 `backend/convert_tensorrt.py:62`；当前主线对应 `cli/embedded-tools/convert_tensorrt.py:65`。

启动同步取得的 PR16 已将 `parser.parse_from_file(source)` 改为 Python 读取 ONNX、序列化后交给 `parser.parse(serialized_model)`，以绕开 Windows 原生文件接口的中文路径问题。候选仍使用旧调用。若直接用包内转换器覆盖主线配套资源，会重新引入该问题。

将当前仓库现有的三个解析回归定向到候选函数后，外置权重拒绝用例通过，中文路径/解析诊断两例因重新调用原生文件接口失败。这是 AST/mock 解析回归，不宣称本轮重新执行了真实 TensorRT GPU 中文路径构建。合入时应在主线转换器上保留中文路径修复，再叠加 `clear_flag(TF32)`。

## 前端整合阻挡项

### 6. [P1] 当前启动器会重新释放旧的帧协议脚本

位置：`cli/Program.cs:1812–1826`、`:1785–1807`。

当前源码会按资源哈希覆盖图片、分段、FlashVSR、BasicVSR++、转换器等脚本；处理顺序脚本另从 EXE 内嵌资源释放。仅覆盖后端目录不能持久启用完整修复。例如旧时序入口仍将帧除以 255，而新共享解码器已经输出 uint16，可能产生严重亮度错误；旧处理顺序脚本仍按 SDR 每像素 3 字节校验，新协议实际为 6 字节。

包内说明已提到此边界，但当前仓库内嵌资源仍未同步，不能把别处“配套修复版 1.3.15 已同步”的说明当作本项目已经完成集成的证据。需要同时更新内嵌脚本、构建新的 EXE，并对旧后端/新启动器的配套关系作明确处理。

### 7. [P1] 混合分段的源切片与拼接仍强制 8bit

位置：`cli/Program.cs:4001`、`:4096`、`:4238`、`:4247`。

含 FFmpeg / Anime4K 段的混合分段任务由 C# 先切片、调用模型组，再统一拼接。模型段源切片固定 `-pix_fmt rgb24`，拼接图的模型/自定义两类分支均固定 `format=rgb24`。即使 Python 分段入口已经改为 RGB48，进入模型前或最终拼接时仍会丢失精度。纯 Python 分段路径与这条混合路径不能混为一谈。

要达到“全面抛弃主处理链 8bit”，必须同时修改这些 C# 路径并核对最终编码参数。另有 RTX 桥接中间文件固定为 HEVC Main10 4:2:0（`Program.cs:365–373`），属于明确的 10bit 边界；它没有变成 16bit 全程，后续应结合 sidecar 实际解码能力单独评估。

## 精度目标与验证边界

- 推荐主帧协议统一为 RGB48/uint16；涉及归一化、缩放、取整时用 FP32。严格保留 16bit 码值的模式还应使用 FP32 模型计算、关闭 TF32；FP16 的 16 位存储不代表有 16bit 整数图像的分辨能力。保留 FP16 速度选项时应明确精度边界。
- 片源原本只有 8bit 时，扩展位深不会恢复已经丢失的信息，但可以减少颜色转换、模型输出、缩放与阶段交接时的再次量化。预览和转场检测的旁路可使用低位深，不能写回主处理链。
- 最终编码可以由用户选 10/12/16bit；中间处理统一 16bit 与成品必须采用 16bit 编码是两个不同约束。当前修复包的输出门槛是至少 10bit，并非一律输出 16bit。
- `disable_tf32` 等新构建参数不会追溯修改旧 Engine。严格精度模式需考虑缓存身份和重建策略；本轮没有对旧 Engine 做真实数值审计，不将缓存风险冒称为已复现的模型错误。
- NCNN RIFE 在此包中被无条件拒绝，以避免原有 8bit 字节接口；应在前端能力和错误提示中同步这一功能变化。FlashVSR 实模型回归仍未验证。
