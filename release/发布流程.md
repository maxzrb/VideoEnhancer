# VideoEnhancer 发布流程

本文是项目的发布前门禁和操作指导。发布分为两条相互独立但需要交叉核对的链路：

- **本体发布**：GitHub Release 为首选版本检查与更新包来源，ModelScope `VideoEnhancer-Releases` 为检查和下载兜底。
- **模型资源发布**：ModelScope `VideoEnhancer-Models` 为模型资源仓库。模型不打包进本体 Release，也不上传到 GitHub Release。

发布完成前，不能只验证其中一条链路。任何一条链路失败，都不要对外宣布“已发布”。

## 1. 发布约定

### 1.1 版本号

- 使用独立 SemVer：`X.Y.Z`，不跟随上游版本号。
- 当前版本唯一源：
  - `VideoEnhancerPlugin/PluginVersion.vb` 的 `PluginVersion.Current`。
  - `cli/VideoEnhancer.csproj` 的 `<Version>`。
- 两处必须完全一致。发布脚本会再次读取并校验，禁止只修改其中一处。
- 已经发布过的版本不得重写或覆盖。发现问题时递增版本发布修正版，例如 `1.0.5` → `1.0.6`。

### 1.2 仓库职责

| 内容 | GitHub | ModelScope |
| --- | --- | --- |
| 版本化 `videoenhancer.exe` | Release 资产 | `VideoEnhancer-Releases` 镜像发布；同时同步到模型页 `Plugin/videoenhancer.exe` |
| `stable.json` | Release 资产，版本检查首选 | 同内容镜像，GitHub 失败时兜底 |
| 超分/补帧/后端模型 | 不发布 | `VideoEnhancer-Models` |
| `PotPlayer.7z` | 不发布 | 不发布 |

### 1.3 本体更新资产

从 1.0.6 起，本体只发布以下两个资产：

```text
VideoEnhancer-<version>-win-x64.exe
stable.json
```

插件 DLL 和布局 JSON 已分别嵌入 EXE/DLL，不再单独发布。更新器替换 EXE 后从新 EXE 释放 DLL，替换前备份，失败自动回滚。不要把模型、Python 环境、FFmpeg、PotPlayer 或其他运行资源放进本体 Release。

从 1.1.0 起，安装后的固定目录结构为：

```text
3FUI\Plugin\
  videoenhancer.3fui.dll
  videoenhancer\
    videoenhancer.exe
    bin\
    models\
    python\
    .videoenhancer-backend-update\
```

GitHub 资产仍保留版本化文件名；安装器和自动更新器负责把它安装为上述固定名称。旧版平铺安装必须通过事务迁移到子目录，迁移前检查占用，迁移中写入恢复日志，失败回滚，意外中断后再次运行可恢复。不得用发布资产名推导安装后的 EXE 名称。

1.0.6 不兼容旧 ZIP 更新协议，不设置 1.0.5 桥接包；旧版用户需要手动下载并运行一次 1.0.6 EXE。

## 2. 发布前门禁

以下项目全部通过后才允许上传。不能用“本地能启动”替代哈希、清单或双源检查。

### 2.1 版本和 Git 状态

- [ ] 已确认本次发布版本和变更范围，版本号未复用历史版本。
- [ ] `PluginVersion.vb` 与 `VideoEnhancer.csproj` 版本一致。
- [ ] `git pull` 已尝试；若因本地改动失败，已确认没有误合并或覆盖风险。
- [ ] `git status` 中只有本次预期修改；没有把临时发布资产、令牌、模型缓存或用户配置加入提交。
- [ ] 版本记录、工作进度和 `docs/codex/STATUS.md` 已准备更新。

### 2.2 依赖和凭据

在 PowerShell 中确认：

```powershell
dotnet --version
gh auth status
modelscope whoami
```

还必须确认：

- [ ] `VideoEnhancerPlugin/build.ps1` 所需的 3FUI 宿主程序集路径存在。
- [ ] GitHub CLI 已登录到有权发布 `maxzrb/VideoEnhancer` 的账号。
- [ ] ModelScope CLI 已登录到有权写入目标数据集的账号。
- [ ] 令牌只存在于登录工具或环境变量，不写入仓库、README、清单或日志。
- [ ] 发布机器有足够磁盘空间；Python 大包、FlashVSR 和模型上传可能占用数 GB 临时空间。

### 2.3 代码、模型和授权门禁

- [ ] GitHub Release Notes 已保存为 UTF-8 文本；每个条目单独一行，且只使用 `[更改]xxxx`、`[新增]xxxx`、`[移除]xxxx` 三种格式，不含空行或自由段落。
- [ ] 已准备上一已发布后端目录和本次候选后端目录。即使认为后端未变化，也必须由脚本逐文件计算 SHA-256 后确认，不能人工跳过。
- [ ] 后端有变化时已递增独立后端版本，并准备与候选目录逐文件一致的完整包及稳定旧版哨兵。
- [ ] 本次功能已完成对应的 CLI、插件和 Python 静态检查。
- [ ] 模型来源、文件名、SHA-256 和再分发状态已有记录。
- [ ] `PotPlayer.7z` 明确排除，任何批量同步命令都没有把它带入上传目录。
- [ ] 未确认授权的模型不得伪装成项目自有内容；至少在发布记录中标注“已确认”或“风险接受”。
- [ ] 不发布不属于本项目目标的上游测试包、旧兼容包或重复归档。

## 3. 构建和本地验收

### 3.1 运行单元和静态检查

在仓库根目录执行：

```powershell
dotnet build cli\VideoEnhancer.csproj -c Release --no-restore
& .\VideoEnhancerPlugin\build.ps1 `
  -HostBin 'C:\path\to\FFmpegFreeUI.6.1.39.extracted' `
  -SkipInstall
python -m unittest cli.tests.test_rve_ordered_backend -v
& .\release\test-release-gates.ps1
& .\release\test-installer.ps1
& .\release\test-updater.ps1
git diff --check
```

安装器和更新器测试必须覆盖全新安装、旧平铺目录迁移、短暂占用重试、持续占用拒绝、注入失败回滚和进程中断恢复。正式构建脚本会在生成候选 EXE 后再次自动运行这两组测试；任一场景失败都不得发布。

先运行只检查、不构建、不上传的发布门禁：

```powershell
& .\release\build-modelscope-release.ps1 `
  -ValidateOnly `
  -NotesFile '.\release\release-notes.txt' `
  -BackendBaseRoot 'D:\backend\published\python' `
  -BackendTargetRoot 'D:\backend\candidate\python' `
  -BackendBaseVersion '2026.08.24.1' `
  -BackendTargetVersion '2026.08.25.1' `
  -BackendFullArchive 'D:\backend\python_20260825.7z' `
  -BackendSentinelPaths 'backend/rve-image-backend.py'
```

后端没有变化时仍必须提供两个目录，且两个后端版本必须相同。检测到变化却没有递增版本、没有完整包、没有稳定哨兵，或完整包与候选目录不一致时，脚本必须失败。

只有用户明确要求“先发布本体、暂缓后端包”时，才允许额外传入 `-DeferBackendPublish`。该模式仍会完成真实目录审计并生成本地增量包，但不会生成或上传 `Backend/channel.json`，也不会上传完整包或补丁；因此它不代表后端已经发布。后续必须重新按标准模式提供与候选目录一致的完整包，完成完整包、补丁和 channel 上传后才能激活后端更新。

如果本次修改了 Python 工具，再执行：

```powershell
python -m py_compile `
  cli\embedded-tools\convert_tensorrt.py `
  cli\embedded-tools\InterpolateRIFE.py `
  cli\embedded-tools\validate_tensorrt_engines.py `
  cli\embedded-tools\TensorRTHandler.py
```

无 NVIDIA 环境时，可以完成构建、协议和隔离测试，但必须在发布记录中明确“未完成真实 TensorRT 构建验证”，不能把静态通过写成 GPU 验收通过。

### 3.2 本地版本和产物检查

```powershell
$installedExe = 'C:\path\to\3FUI\Plugin\videoenhancer\videoenhancer.exe'
& $installedExe --version
& $installedExe --list-download-models --json > $env:TEMP\videoenhancer-models.json
```

确认：

- [ ] `--version` 与本次发布版本一致。
- [ ] 模型清单中最多只有一个 `Plugin/videoenhancer.exe` 路径。
- [ ] 预置 TensorRT Engine 不会被新客户端当作必需发布资源。
- [ ] 模型清单没有 `PotPlayer.7z`。
- [ ] 3FUI 插件页显示的处理程序路径为 `Plugin\videoenhancer\videoenhancer.exe`，环境检测通过且模型下拉可读取。
- [ ] 使用上述实机安装路径完成当前发布要求的 GPU 矩阵；本次 1.1.0 门禁为 679 项、五路并行，OOM 只允许记录为 `SKIP_OOM`，其他失败必须修复并复测。

## 4. 生成本体发布包

先只构建、不上传，确认本地包无误：

```powershell
& .\release\build-modelscope-release.ps1 `
  -Version '1.0.6' `
  -HostBin 'C:\path\to\FFmpegFreeUI.6.1.39.extracted' `
  -NotesFile '.\release\release-notes.txt' `
  -BackendBaseRoot 'D:\backend\published\python' `
  -BackendTargetRoot 'D:\backend\candidate\python' `
  -BackendBaseVersion '2026.08.24.1' `
  -BackendTargetVersion '2026.08.25.1' `
  -BackendSentinelPaths 'backend/rve-image-backend.py' `
  -DeferBackendPublish
```

上例是本体先行的暂缓模式，不会上传或激活后端。常规发布必须去掉 `-DeferBackendPublish`，并提供 `-BackendFullArchive`。

脚本生成：

```text
release/dist/modelscope/stable.json
release/dist/modelscope/releases/<version>/VideoEnhancer-<version>-win-x64.exe
release/dist/modelscope/release-notes.txt
release/dist/backend-update/backend-release-audit.json
release/dist/backend-update/channel.json（后端变化且未暂缓时）
release/dist/backend-update/<base>_to_<target>.7z（仅后端变化时）
```

检查清单和 EXE：

```powershell
$version = '1.0.6'
$exe = "release\dist\modelscope\releases\$version\VideoEnhancer-$version-win-x64.exe"
Get-FileHash -Algorithm SHA256 $exe
Get-Content -Raw -Encoding UTF8 release\dist\modelscope\stable.json
& $exe --version
```

- [ ] `stable.json.version` 和 CLI 版本一致。
- [ ] `stable.json.package.path` 指向当前版本目录，不指向旧版本。
- [ ] `stable.json.package.size/sha256` 与 EXE 实际大小/哈希一致。
- [ ] EXE 可运行、报告正确版本，并包含可释放的 `videoenhancer.3fui.dll` 资源。

## 5. 更新器隔离测试

必须在上传前运行：

```powershell
& .\release\test-updater.ps1 -Version '1.0.6'
& .\release\test-backend-updater.ps1
& .\release\test-release-gates.ps1
```

结果必须包含：

```text
PASS: success / tamper / invalid-package / rollback
```

该测试覆盖：

- 正常替换 EXE，并从新 EXE 释放 DLL。
- 拒绝被篡改或与临时更新器不一致的 EXE。
- 拒绝无效更新资产。
- DLL 替换失败时完整回滚 EXE 和 DLL。

## 6. 发布本体到双源

### 6.1 发布顺序

后端有变化时，必须先完成 ModelScope Backend 的“完整包 → 增量包 → `channel.json`”并回读核对，再创建 GitHub Release；这是为了避免新 EXE 已发布但后端更新通道尚不可用。后端没有变化时，本体仍按先 GitHub、后 ModelScope Releases 的顺序发布。

用户明确授权暂缓 Backend 发布时，可用 `-DeferBackendPublish` 只发布本体。脚本仍会审计和生成本地补丁，但跳过所有 Backend 上传与 channel 激活；发布记录必须明确标注后端未发布，不能把该模式作为常规流程。

### 6.2 一键发布

确认门禁全部通过后，git提交更改到GitHub远端，并执行：

```powershell
& .\release\build-modelscope-release.ps1 `
  -Version '1.0.6' `
  -HostBin 'C:\path\to\FFmpegFreeUI.6.1.39.extracted' `
  -NotesFile '.\release\release-notes.txt' `
  -BackendBaseRoot 'D:\backend\published\python' `
  -BackendTargetRoot 'D:\backend\candidate\python' `
  -BackendBaseVersion '2026.08.24.1' `
  -BackendTargetVersion '2026.08.25.1' `
  -BackendFullArchive 'D:\backend\python_20260825.7z' `
  -BackendSentinelPaths 'backend/rve-image-backend.py' `
  -PublishGithub `
  -PublishModelScope
```

脚本会：

1. 重新构建插件和单文件 CLI。
2. 用 CLI `--version` 做版本一致性校验。
3. 校验逐行分类 Release Notes，并对前后端目录逐文件计算大小和 SHA-256。
4. 后端有变化时验证完整包与目标目录逐文件一致，自动生成增量包、`channel.json` 和审计 JSON。
5. 按“完整后端包 → 增量包 → `Backend/channel.json`”顺序上传并回读核对；完成后才允许创建 GitHub Release。
6. 生成版本化 EXE、`stable.json` 和 `release-notes.txt`。
7. 使用 `--notes-file` 创建 GitHub `v<version>` Release，上传 EXE 和 `stable.json`。
8. 将本体目录上传到 `AerithDream/VideoEnhancer-Releases`，并同步 EXE 到模型页兜底路径。

如果脚本在 GitHub 成功、ModelScope 失败，不要重新生成不同内容的包；保留本次 `dist`，修复登录/网络问题后只重试 ModelScope 上传，并重新做远端核对。

## 7. 发布模型资源

模型资源必须单独准备上传目录，不要直接把整个仓库根目录交给 ModelScope CLI。

### 7.1 上传前清单

- [ ] 目标仓库为 `AerithDream/VideoEnhancer-Models`，类型明确为 `dataset`。
- [ ] 目录结构符合 CLI 允许的根目录：`Backend`、`BasicVSR++`、`Bin`、`FlashVSR`、`Frame-Interpolation`、`ONNX`、`Param-Bin`、`Plugin`、`RIFE`、`PTH`。
- [ ] `PotPlayer.7z` 不在上传目录。
- [ ] 同一模型只有一个当前推荐路径；旧兼容归档不因习惯自动继续同步。
- [ ] 每个大文件已记录大小和 SHA-256。
- [ ] 本体兜底文件 `Plugin/videoenhancer.exe` 如需保留，资源列表只出现一次；“下载全部”不会批量下载它。

### 7.2 上传命令

```powershell
modelscope upload `
  AerithDream/VideoEnhancer-Models `
  'D:\staging\VideoEnhancer-Models' `
  --repo_type dataset
```

涉及同路径文件替换、缓存异常或上次上传中断时：

- 先确认本地文件和目标路径，没有直接执行删除或同步清理。
- 必要时清理本地上传缓存后使用 `--no-cache` 重试。
- 不使用未审查的 `--sync` 或递归删除操作。

### 7.3 模型远端验收

```powershell
$installedExe = 'C:\path\to\3FUI\Plugin\videoenhancer\videoenhancer.exe'
& $installedExe --list-download-models --json > $env:TEMP\remote-models.json
```

- [ ] 预期模型全部出现，分页读取没有漏项。
- [ ] 每个远端文件大小与本地记录一致。
- [ ] 随机下载至少一个新增模型，CLI 校验 SHA-256 通过。
- [ ] RIFE、NCNN、TensorRT 权重没有因目录兼容逻辑重复显示。
- [ ] `Plugin/videoenhancer.exe` 若存在，路径唯一且不混入模型解压目录。

### 7.4 后端增量更新

Backend 不再作为普通模型压缩包覆盖解压。发布脚本每次都强制比较上一已发布目录与候选目录，不能用“本次应该没改后端”跳过。也可单独执行：

```powershell
& .\release\prepare-backend-update.ps1 `
  -BaseRoot 'D:\backend\20260824\python' `
  -TargetRoot 'D:\backend\20260825\python' `
  -BaseVersion '2026.08.24.1' `
  -TargetVersion '2026.08.25.1' `
  -FullArchive 'D:\backend\python_20260825.7z' `
  -OutputRoot 'D:\staging\backend-update' `
  -SentinelPaths 'backend/rve-image-backend.py'
```

脚本生成 `backend-release-audit.json`、增量包和 `channel.json`，并强制满足：

- `latestVersion` 指向本次后端版本，版本号发布后不可复用。
- `full` 与每条 `patches` 必须填写实际字节数和 SHA-256。
- `legacyBaselines` 的哨兵应选完整版本中稳定且能区分版本的文件；不要只选可能被旧 CLI 自修补的脚本。
- 补丁中的路径均相对 `CoreRoot\python`；删除旧脚本必须显式生成 `delete` 操作。
- 完整包解压后的文件集合、大小和 SHA-256 必须与候选后端目录逐项一致；发现旧文件、多文件、少文件或内容不同均停止发布。
- 后端文件有变化时版本必须递增；没有变化时版本必须保持相同，禁止空版本更新。
- 上传前运行 `release/test-backend-updater.ps1`，覆盖增量成功、冲突拒绝及完整修复提示、自动回滚、中断恢复、强制完整修复和幂等补写标记。
- 先上传完整包和补丁，最后上传 `channel.json`，避免客户端先看到尚未就绪的更新通道。
- 插件的三路并行和“下载全部”不得包含 Backend；Backend 只允许通过 `--update-backend` 更新。

### 7.5 GitHub Release Notes 固定格式

Release 正文不得使用自由段落，也不得把多个事项写在同一行。模板见 `release/release-notes.example.txt`：

```text
[更改]修复 GMFSS 模型读取错误
[更改]缩短补帧模型列表加载时间
[新增]加入后端文件级增量更新
[移除]移除 Backend 覆盖解压入口
```

- 只允许 `[更改]`、`[新增]`、`[移除]`，标签必须位于行首。
- 标签后必须立即填写内容；每个条目单独一行，不允许空行。
- 同一分类可以出现多行；没有对应变化的分类可以不写。
- `stable.json.notes` 与 GitHub Release 正文使用同一内容；GitHub CLI 必须使用 `--notes-file`，避免换行被命令行转义破坏。
- 发布后读取 GitHub Release 正文，逐行再次校验；任一行不合规都不算发布完成。

## 8. 双源交叉核验

发布后必须核对同一版本的版本号、路径、大小和哈希：

```powershell
$version = '1.0.6'
$gh = Invoke-RestMethod `
  -Uri 'https://api.github.com/repos/maxzrb/VideoEnhancer/releases/latest' `
  -Headers @{ Accept = 'application/vnd.github+json'; 'User-Agent' = "VideoEnhancer/$version" }
$ghStable = Invoke-RestMethod `
  -Uri (($gh.assets | Where-Object { $_.name -eq 'stable.json' }).browser_download_url) `
  -Headers @{ 'User-Agent' = "VideoEnhancer/$version" }
$msStable = Invoke-RestMethod `
  -Uri 'https://www.modelscope.cn/datasets/AerithDream/VideoEnhancer-Releases/resolve/master/stable.json'
```

必须满足：

- [ ] GitHub latest tag 为 `v<version>`。
- [ ] GitHub Release 正文每个非空行均匹配 `^\[(更改|新增|移除)\]\S.*$`，并与本地 `release-notes.txt` 完全一致。
- [ ] GitHub `stable.json.version` 等于 `<version>`。
- [ ] ModelScope `stable.json.version` 等于 `<version>`。
- [ ] 两份清单的 `package.path`、`package.size`、`package.sha256` 完全一致。
- [ ] GitHub EXE 下载地址和 ModelScope resolve 地址均返回 HTTP 200/有效重定向。
- [ ] ModelScope 数据集 README 没有写反下载优先级。
- [ ] GitHub Release 资产只有 `stable.json` 和版本化 EXE，不含模型大包。
- [ ] 模型仓库 `Plugin/videoenhancer.exe` 与 Release EXE 的 SHA-256 一致。

网络受限环境还应手动验证一次：让 GitHub 请求失败，确认插件能读取 ModelScope 清单并下载同一 EXE。不能只验证“两个 URL 都能访问”，因为那不能证明兜底分支真的被执行。

## 9. 发布失败和回滚

### 9.1 本体发布失败

- 构建失败：修复源码后重新构建，不上传半成品。
- EXE/清单哈希不一致：丢弃本地生成目录，重新生成，不手工编辑哈希。
- GitHub 已发布但包有问题：不要覆盖既有 Release 资产，递增补丁版本发布修正版。
- ModelScope 上传失败：保留同一份 `dist`，修复认证/网络后重试；不要重新打包出不同哈希。
- 双源版本不一致：暂停公告和自动更新，先恢复 ModelScope `stable.json` 与 GitHub 资产一致。

### 9.2 模型资源失败

- 单个模型损坏：先停止推荐该资源，再上传修正版并更新哈希记录。
- 远端出现重复路径或旧归档：新客户端先过滤；远端删除前必须明确列出路径、大小和影响范围。
- 发现授权或来源问题：停止继续分发该文件，记录风险和处理决定；不得用项目许可证替代第三方权重许可。

### 9.3 不要做的事

- 不要 `git reset --hard` 或用强制 checkout 清理工作树。
- 不要把令牌写进 PowerShell 历史以外的仓库文件、脚本或日志。
- 不要直接覆盖已公开版本的 EXE、`stable.json` 或 GitHub Release。
- 不要在未退出 3FUI 时强行替换正在加载的 DLL。

### 10.1 默认提交与推送

```powershell
git status --short --branch
git add README.md VideoEnhancerPlugin cli release docs/codex version
git commit -m "release: <version>"
git push fork HEAD:main
git status --short --branch

```

- [ ] 推送目标已确认是独立维护仓库 `fork`，不是 `origin` 上游仓库。
