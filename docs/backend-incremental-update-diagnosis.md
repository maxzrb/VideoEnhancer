# 后端增量更新设备差异诊断

日期：2026-11-14

## 结论

数据库中已经有 `2026.09.30.1` 或更早版本的设备中，是否能在升级到 `v1.3.17` 后直接应用增量补丁，主要取决于用户是否在该后端更新前先用 `v1.3.17` 执行过一次普通视频、图片或模型探测命令。

`v1.3.17` 在普通命令开始时会把内嵌高精度核心同步到本地后端。同步后的文件内容属于 `2026.11.09.2`，但本地后端版本标记仍可能是 `2026.09.30.1`。后端更新器随后选择：

```text
2026.09.30.1 -> 2026.11.09.1 -> 2026.11.09.2
```

第一段补丁要求 `backend/src/pytorch/UpscaleTorch.py` 的旧值为：

```text
fa95f86ae21d5b6e8380ebe89e1a86c6baceecd866ff87586d01467025e97e19
```

但 `v1.3.17` 内嵌核心已经把它同步为第二段补丁的终值：

```text
9a94d4840b1c91b6d1f444797b9b6f88f1d74dfb49bf91e42dffee693f0fdc94
```

第一段补丁不接受该“提前到达后续版本”的文件，输出 `BACKEND_FULL_REQUIRED`。下载页因此切换到完整修复包。

## 调用链

1. `--backend-status` 和 `--update-backend` 在版本入口直接返回，不触发内嵌核心同步。
2. 普通视频、图片、模型探测等命令继续执行 `EnsureInterpolationSupportScripts()`。
3. `RveHighBitDepthSupport.Install()` 按内嵌资源哈希更新核心脚本，并保留已有的 `.videoenhancer-backend.json` 版本标记。
4. 后续更新继续按该标记选择补丁链。
5. `BackendUpdateManager.ValidatePatchFiles()` 对替换文件只接受当前段的旧哈希、目标哈希；旧文件已等于后续段目标值时仍会判为冲突。
6. `ApplyBackendPatchArchive()` 捕获该异常并统一输出 `BACKEND_FULL_REQUIRED`，前端据此显示完整修复包。

## 隔离复现矩阵

| 设备状态 | 后端标记 | 是否先运行 `v1.3.17` | 结果 |
| --- | --- | --- | --- |
| 原始 `2026.09.30.1` | `2026.09.30.1` | 否 | 两段补丁成功，最终 `2026.11.09.2` |
| 原始 `2026.09.30.1` | `2026.09.30.1` | 是 | 第一段补丁在 `UpscaleTorch.py` 哈希处失败，要求完整包 |
| 旧后端无版本标记 | 无 | 是 | 单文件哨兵可能误判为 `2026.11.09.1`，跳过第一段补丁后因新增说明文件缺失而失败 |

第一条对照在隔离目录中依次应用 `2026.09.30.1 -> 2026.11.09.1` 和 `2026.11.09.1 -> 2026.11.09.2`，退出码均为 0，最终状态为 `current`。第二条对照先执行普通命令完成内嵌核心同步，再应用第一段补丁，退出码为 1，错误明确指向 `UpscaleTorch.py` 旧文件哈希不匹配。

## 版本来源核对

- `v1.3.16` 发行提交 `c7f46be` 中的 `UpscaleTorch.py`，按 Windows 工作树的 CRLF 内容计算，SHA-256 为 `fa95f86a...`，正好是第一段补丁目标值。
- `v1.3.17` 发行提交 `41f7a92` 中的同一文件，按 CRLF 内容计算，SHA-256 为 `9a94d484...`，正好是第二段补丁终值。
- 第二段补丁正是以 `fa95f86a...` 为旧值、`9a94d484...` 为新值。

因此，该设备差异由 `v1.3.17` 先同步内嵌核心、后更新独立后端的状态组合引入，并非下载是否成功或远端补丁随机损坏。

## 其他失败类型

`ApplyBackendPatchArchive()` 也会把文件占用、权限不足、杀毒软件拦截、Python 健康检查超时或取消统一包装成完整包提示。没有设备日志时，无法从当前界面区分这些临时失败与上述确定性哈希冲突。应优先修复已复现的版本链问题；再把“内容确定不兼容”和“可重试的临时失败”区分为不同结果。

## 建议修复方向

1. 更新时先读取整条补丁链的清单，允许当前文件等于后续补丁目标哈希时暂时跳过，由后续段完成版本标记推进。
2. 增加回归用例：`2026.09.30.1` 标记 + `v1.3.17` 内嵌核心已经同步；期望两段补丁均成功。
3. 无版本标记的后端不要只用单个哨兵推断完整版本；应同时验证补丁链所需新增文件，或在首次同步内嵌核心前保存基线版本。
4. 区分 `BACKEND_PATCH_INCOMPATIBLE` 与可重试的临时错误，避免文件锁或健康检查超时直接引导用户下载数 GB 完整包。

公开的 `v1.3.17` 标签、资产和后端补丁保持冻结。本诊断不修改正式安装，也不改写已发布版本。
